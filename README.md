# Multi-Agent Dev Assistant

> 基于多 Agent 辩论机制的智能开发辅助系统

## 项目简介

Multi-Agent Dev Assistant 是一个通用的开发辅助系统，通过多 Agent 辩论机制，帮助开发者做技术决策、方案评估、代码审查、架构设计等。

**核心理念**：不是替代你写代码，而是帮你想清楚怎么写。

## 解决的问题

| 问题 | 传统方式 | 多 Agent 方式 |
|------|----------|---------------|
| 技术选型 | 网上搜，凭经验 | 多视角辩论，有理有据 |
| 方案评估 | 想到啥做啥 | 系统性评估可行性/成本/风险 |
| 代码审查 | 自己看，容易漏 | 多维度审查，不遗漏 |
| 架构设计 | 拍脑袋 | 多团队讨论，最优方案 |
| 问题排查 | 试错 | 分析根因，系统性解决 |

## 核心特性

- **多 Agent 辩论**：6 个专业团队从不同视角对抗推演
- **8 种辩论模式**：适配不同场景的决策机制
- **六阶工作流**：从方向到交付的完整闭环
- **三层约束**：Harness Engine（硬拦截）+ AGENTS.md（规范）+ SOUL.md（风格）
- **意图驱动**：只说"要什么"，不说"怎么做"
- **通用适用**：任何项目、任何技术栈都能用
- **可移植**：换公司、换项目都能带走

## 架构设计

```
你提出问题
    ↓
┌─────────────────────────────────────────┐
│           辩论层                         │
├──────────┬──────────┬──────────┬────────┤
│ 技术专家 │ 架构专家 │ 成本专家 │ 风险专家│
│          │          │          │        │
│ "用React │ "建议微   │ "开发成本│ "技术债 │
│ 更合适"  │ 服务架构" │ $5000"  │ 风险高" │
└──────────┴──────────┴──────────┴────────┘
    ↓ 辩论讨论
┌─────────────────────────────────────────┐
│           决策层（你）                    │
│  评估：技术可行性 + 成本 + 风险          │
│  决策：批准/驳回/修改方案                │
└─────────────────────────────────────────┘
    ↓ 执行
输出：决策报告 + 理由 + 风险提示
```

## 辩论团队

| 团队 | 视角 | 职责 |
|------|------|------|
| Tech Expert | 技术 | 技术选型，可行性评估 |
| Architect | 架构 | 系统设计，模块划分 |
| Cost Analyst | 成本 | 开发成本，维护成本 |
| Risk Assessor | 风险 | 技术债，安全风险 |
| Quality Engineer | 质量 | 代码规范，测试覆盖 |
| Performance Engineer | 性能 | 性能优化，扩展性 |

## 辩论模式

| 模式 | 适用场景 |
|------|----------|
| adversarial_debate | 技术选型（A vs B） |
| jury_panel | 方案评审（多团队投票） |
| risk_priority_matrix | 风险评估（高/中/低分级） |
| cost_benefit_analysis | 成本收益分析 |
| delphi_method | 专家意见收敛 |
| six_thinking_hat | 六顶思考帽 |
| swot_analysis | 优劣势分析 |
| red_team | 红队攻击测试 |

## 应用场景

### 1. 技术选型

```
你： "这个项目用 MongoDB 还是 PostgreSQL？"

辩论结果：
┌─────────────────────────────────────────┐
│ MongoDB                                 │
│ 优点：文档型数据友好，开发快            │
│ 缺点：查询复杂数据性能差，云服务贵      │
│ 风险：数据一致性较弱                    │
├─────────────────────────────────────────┤
│ PostgreSQL                              │
│ 优点：查询性能好，成熟稳定，功能丰富    │
│ 缺点：文档型数据处理稍复杂              │
│ 风险：学习曲线较陡                      │
├─────────────────────────────────────────┤
│ 推荐：PostgreSQL                        │
│ 理由：长期维护成本更低，技术栈更主流    │
│ 置信度：0.85                            │
└─────────────────────────────────────────┘
```

### 2. 方案评估

```
你： "我想做一个实时聊天功能"

辩论结果：
┌─────────────────────────────────────────┐
│ 技术方案：WebSocket + Redis             │
│ 开发成本：3 人 × 2 周 = $6000           │
│ 维护成本：每月 $200（服务器）            │
│ 风险：高并发时可能有性能瓶颈            │
│ 建议：先做 MVP，验证需求后再扩展        │
│ 置信度：0.80                            │
└─────────────────────────────────────────┘
```

### 3. 代码审查

```
你： "帮我审查这段代码"

审查结果：
┌─────────────────────────────────────────┐
│ 代码质量：7/10                          │
├─────────────────────────────────────────┤
│ 问题：                                  │
│ 1. 命名不规范（P1）                     │
│ 2. 缺少错误处理（P1）                   │
│ 3. N+1 查询（P2）                       │
│ 4. 缺少注释（P3）                       │
├─────────────────────────────────────────┤
│ 建议：                                  │
│ 1. 重构函数命名，使用描述性名称         │
│ 2. 添加 try-catch 和日志                │
│ 3. 使用 JOIN 替代循环查询               │
│ 4. 添加关键逻辑注释                     │
└─────────────────────────────────────────┘
```

### 4. 架构设计

```
你： "这个系统怎么设计？"

辩论结果：
┌─────────────────────────────────────────┐
│ 方案A：单体应用                         │
│ 优点：简单，开发快，部署方便            │
│ 缺点：扩展性差，耦合度高                │
│ 适用：初期，团队小                      │
├─────────────────────────────────────────┤
│ 方案B：微服务                           │
│ 优点：扩展性好，独立部署                │
│ 缺点：复杂度高，运维成本高              │
│ 适用：成熟期，团队大                    │
├─────────────────────────────────────────┤
│ 推荐：先单体，后续拆分                  │
│ 理由：当前团队小，快速验证需求更重要    │
│ 路径：单体 → 模块化 → 微服务            │
└─────────────────────────────────────────┘
```

### 5. 问题排查

```
你： "这个接口响应很慢，怎么优化？"

诊断结果：
┌─────────────────────────────────────────┐
│ 问题：API 响应时间 5 秒（目标 < 1 秒）  │
├─────────────────────────────────────────┤
│ 根因分析：                              │
│ 1. 数据库查询慢（主因，占 80%）         │
│ 2. 没有缓存（次因，占 15%）             │
│ 3. 代码逻辑低效（次因，占 5%）          │
├─────────────────────────────────────────┤
│ 优化建议：                              │
│ 1. 添加数据库索引（预计提升 70%）       │
│ 2. 引入 Redis 缓存（预计提升 20%）      │
│ 3. 优化查询逻辑（预计提升 10%）         │
├─────────────────────────────────────────┤
│ 预期效果：响应时间 < 500ms              │
│ 实施成本：1 人 × 2 天                   │
└─────────────────────────────────────────┘
```
